# Flosi — seguridad de la candidata de desarrollo

Fecha: 29 de octubre de 2026, America/New_York. Continuación de `300375424f8a2f8e0c8a602a27cab9ca9637620a`; fuente OpenWhispr v1.10.4, `ba6d61820b4c56d7b08012c61c2ae6b43f3152f3`. No se repite la auditoría funcional inicial. El objetivo es preparar QA aislada, no certificar seguridad para distribución o uso cotidiano.

## Preservación y alcance

La rama `codex/flosi-baseline` se publicó en **sseaccorp/openwhispr**, preservando el SHA exacto `30037542`. PR borrador: <https://github.com/sseaccorp/openwhispr/pull/1>. Su base es `flosi/upstream-v1.10.4`, creada en `ba6d6182`; el `main` del fork ya era 1.11.0 y no se mezcla con esta preparación. No hubo force push, merge, release, publicación de instaladores ni escritura al repositorio original.

El único cambio funcional de composición es en dependencias. No hay modificaciones en `main.js`, `preload.js`, `src/`, helpers nativos, scripts de motores, prompts, modelos, parámetros, identidad, configuración Electron, autenticación o monetización. Las versiones de Electron, SQLite, ONNX, Whisper, sherpa y llama se mantienen. Las decisiones de alto riesgo quedan propuestas, sin ejecutarse.

## Exposición por paquete

### Better Auth 1.6.27 — crítica pendiente en el inventario; explotación local no identificada

Es dependencia de producción; trae `@better-auth/core`, adaptadores Drizzle/Kysely y otros módulos. `@better-auth/sso@1.6.27` es otro cliente instalado. El escritorio importa `createAuthClient` de `better-auth/react` y `ssoClient` de `@better-auth/sso/client` en `src/lib/auth.ts`; el servidor por defecto es `https://auth.openwhispr.com`. No se encontró una instancia `betterAuth(...)` ni servidor Magic Link/OAuth Proxy/device authorization en el código desktop auditado. Tener archivos de servidor en node_modules no crea sus endpoints.

### Electron 41.10.7 — alta pendiente y relevante para el producto

Figura en devDependencies porque construye/empaqueta la app, pero **Chromium y Node embebidos se entregan con el ejecutable**. `npm audit --omit=dev` no lo evalúa y puede dar una impresión equivocada de seguridad de producción.

- **[GHSA-jr5w-w6x2-84p9](https://github.com/advisories/GHSA-jr5w-w6x2-84p9), alta:** intermediarios eMudhra comprometidos pueden permitir suplantación TLS ante un atacante capaz de interceptar la conexión. La app sí hace HTTPS para cuentas, modelos, APIs y actualizaciones; no se puede excluir su aplicabilidad. El aviso cubre Chromium y Node y dice que no hay workaround del lado de la app. Versiones corregidas incluyen **42.11.16**, 43.8.1 y posteriores de las ramas indicadas. No se encontró una 41 corregida en el registry consultado.
- Moderadas: [HID/USB](https://github.com/advisories/GHSA-fw47-9c62-h3vw), [SameSite de ventanas abiertas](https://github.com/advisories/GHSA-2p8c-gr87-2676), [pointer lock](https://github.com/advisories/GHSA-x562-297c-g43g) y [openExternal](https://github.com/advisories/GHSA-997q-gvvc-jwmx). No se observó uso de WebHID/WebUSB ni pointer lock en el producto, y `windowManager.js` deniega ventanas nuevas y navegación externa dentro del renderer. Sí existe apertura de enlaces y protocolos, por lo que esas defensas reducen rutas concretas, sin demostrar inmunidad ante un renderer comprometido.
- Bajas: [extensiones/tabs](https://github.com/advisories/GHSA-98mx-cjp9-gchm) y geometría de frames [general](https://github.com/advisories/GHSA-3qxv-5xgr-q7w9)/[offscreen macOS](https://github.com/advisories/GHSA-h3v5-h239-pg29). No se encontró carga de extensiones ni renderizado offscreen/frame subscription. La última además no es una ruta Windows. Permanecen en el inventario del runtime.

**Corrección propuesta, no aplicada:** candidato separado con Electron **42.11.16** fijado, reconstrucción de SQLite para su nueva ABI y QA de permisos, micrófono, GPU/composición, ventanas, foco/pegado, updater y empaquetado Windows. Consultar también cambios incompatibles de Electron 42. No saltar a la 45 que propone audit por defecto. Es un cambio de runtime que requiere autorización y validación nativa; esta fase mantiene 41.10.7 para no sustituir una base no comprobada por otra. No se desactivó TLS, sandbox, Defender o SmartScreen para compensarlo.

### Zod — corregido; exposición transitiva de parsing

[GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), alta, afecta versiones anteriores a 4.6.6 al acumular errores de colecciones grandes. Zod 4 se distribuye como dependencia directa/peer de AI SDK y también aparece en Better Auth/SSO. El código de herramientas usa esquemas de AI SDK; no se encontró un `z.array` llamado directamente por código desktop. Respuestas/argumentos externos y parsing transitivo impiden certificar una ausencia total de ruta sin trazado dinámico. Se corrige a la primera versión parcheada del mismo major; el alcance de regresión incluye tool schemas, respuestas de proveedores y tipos. No es una corrección del algoritmo de transcripción.

### Happy DOM — corregido; riesgo del runner, no del Chromium entregado

DevDependency usada en `test/` para renderers simulados. Los avisos son [import alias/ejecución de código host](https://github.com/advisories/GHSA-834v-8h66-3h79), [SSRF de iframe/CSS](https://github.com/advisories/GHSA-c8p4-j97h-3vg8) y [cookies](https://github.com/advisories/GHSA-5fpq-26gf-qwcr). Explotación requiere contenido controlado por atacante en las APIs afectadas, y en el primer caso evaluación JS habilitada. Los fixtures se construyen en el repositorio; no hay servicio de preview remoto de usuarios usando Happy DOM. Los PR no confiables ya pueden contener código de tests: la actualización no convierte ese runner en sandbox seguro. No dar secretos al CI de contribuciones externas.

21.0.4 es el primer patch que cubre todos estos avisos. Se adopta aunque cambie el major por su alcance exclusivo de tests, revisión del cambio y regresión completa. No se modificó ningún test para restaurar la carga insegura de iframes/CSS. No se presenta un cambio de Happy DOM como corrección del sandbox del Electron real.

### Riesgo moderado restante

`fast-uri` es transitivo de validación de herramientas de desarrollo/build y no aparece en el audit omit-dev. Sus cuatro GHSA (`w74x-v6f9-j3xg`, `xhq7-xmqj-769h`, `wjr9-j795-jxcr`, `333x-w4r6-6crp`) afectan normalización, esquema y equivalencia de URI antes de 3.1.9. No se identificó como validador de enlaces del producto. Propuesta separada: patch compatible a 3.1.9, verificar consumidores y repetir lint/build; no se amplía este cambio automáticamente a otros paquetes fuera del objetivo crítica/altas.

## Verificación y límites

Instalación desde lockfile, quality-check (lint/formato/typecheck) y build del renderer aprobados. Los avisos previos de variables/react-refresh y tamaño de chunks permanecen. `npm audit` sigue devolviendo exit 1: **no hay gate de seguridad verde**. La suite completa se vuelve a ejecutar porque cambió Happy DOM y el parsing transitivo de Zod; no es una repetición de la auditoría inicial. Resultado final: **8.713 aprobadas, 0 fallos, 0 canceladas, 32 omitidas y 1 TODO**, de 8.746 casos enumerados, en 1.293,61 s. Las omisiones de plataforma/entorno y el TODO histórico de sync quedan identificados en `flosi-phase2-evidence/RESULTS.json` y no se cuentan como aprobados. No hubo cambios de tests para conseguirlo.

Las búsquedas estáticas y los contratos unitarios no son un pentest ni prueba de no explotabilidad. No se atacó el servidor OpenWhispr, no se usaron claves reales y no se probaron cuentas del propietario. Los problemas heredados de `webSecurity:false`, sandbox del control panel, CSP parcial, namespaces y actualización upstream siguen descritos en la auditoría inicial. No se cambian aquí para eludir restricciones del entorno. La sintaxis de los cinco bloques PowerShell y el forwarding de argumentos npm se comprobaron con PowerShell 7.6.0 en Linux (archive oficial con SHA-256 verificado); las llamadas Windows se analizaron, no se ejecutaron. Windows, GPU RTX y el instalador siguen **no ejecutados en Codex Cloud**.

## Decisión antes del rediseño

La candidata sirve para **pruebas funcionales controladas con audio ficticio/licenciado, perfil/OS aislado y procesamiento local**, no para distribuirla como producto seguro. Bloqueos P0: decisión de runtime Electron y aprobación de su actualización; contratos/seguridad de cuentas antes de usarlas; pruebas Windows del flujo completo; derechos de recursos y cumplimiento de paquetes; aislamiento del producto antes de coexistencia normal. No es necesario rehacer motores para resolver ninguno de estos puntos.
